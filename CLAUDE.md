# CLAUDE.md — working with the caOS FREE package

Guidance for an AI coding assistant (Claude Code or similar) helping a user write firmware
on top of this package. It applies to the FREE edition: precompiled libraries, public
headers, examples and manuals — **no kernel or driver sources**.

## What is in the package

| Path | Content |
|---|---|
| `include/` | Public headers. `caos.h` includes all of them. This is the API reference. |
| `include/os_config.h` | The configuration the libraries were built with. **Fixed**: do not edit. |
| `<fam>/<mcu>/` | `libcaOS.a`, `libcaOS_<MCU>.a`, linker script, `objmap.h` (board map: LEDs, UARTs, stack sizes, tick) |
| `examples/example_N/` | `ca_os_exN.c` — one feature per example, plus PC-side test scripts |
| `workspace/app_N/` | The user's applications, one firmware each; `app_1` is the template. `app_2` (bootloader: TFTP/DFU update, A/B slots, rollback), `app_4` … are complete reference applications with their guides and PC scripts |
| `doc/` | the manual in five volumes: `caos_vol1_features` (how caOS works), `caos_vol2_examples`, `caos_vol3_quickstart` (build, flash, porting) in English (`_en`) and Italian (`_it`); `caos_vol4_reference_en` (every function, type, define) and `caos_vol5_qa_en` (questions and answers), English only; `caos_overview_en.pdf`: how caOS works, what it measures, where it is weak (the scheduler model, heap, network, crypto, limits) |
| `tools/lookup_sym.py` `tools/lookup_qa.py` `tools/db/` | API lookup: reference and Q&A, offline (see "Finding an API") |
| `new_app.py` | Generates a new `workspace/app_N` skeleton (tasks, names, levels, stacks) |
| `peek.py` | Reads/writes a variable of the running firmware by name, through the CLI (no debugger) |
| `prog.sh` `reset_mcu.sh` | Flash and reset through the ST-LINK (`STM32_PRG_PATH` must point to STM32CubeProgrammer) |
| `test/` `eol.sh` | The test bench used to validate caOS, and the end-of-line run over every board |
| `simu/` | Renode simulation: the same `.elf` on a simulated NUCLEO (see "Running without a board") |
| `README.md` `QUICKSTART.md` `EXAMPLES.md` `LIMITS.md` | Start here; `LIMITS.md` says what the FREE edition leaves out |

Supported boards: NUCLEO-F439ZI, -F446ZE, -F767ZI, -H563ZI, -H753ZI, -H7S3L8, -U575ZI-Q.
On the NUCLEO-H7S3L8 (H773) the firmware runs from the XSPI2 Octo-SPI flash: the
trampoline `workspace/app_5` must be in the internal flash first (`./prog.sh -s -a 5`).

## Build and run

```bash
./bootstrap -m H563     # pick the board (F439 F446 F767 H563 H753 H773 U575), writes cpu.cmake
./do                    # all examples      -> elfs/<MCU>/<mcu>_example_N.elf
./do 1 33               # some examples
./new_app.py -t sensor:4 -t logger:2   # new workspace/app_N skeleton (no -t: asks)
./do -a 1               # an application in workspace/app_1
./prog.sh -s -e 1       # flash example 1 (-a N: app_N, -f FILE: any .elf)
./clean
```

The user builds and flashes. When something fails, ask for the compiler output or the
console log rather than guessing.

## Finding an API

Use the two lookup tools **before** writing a call to a caOS function you have not seen in
this conversation, and before reading a header by hand:

```bash
tools/lookup_sym.py ca_uart_put          # signature, header, parameters, return, notes, example
tools/lookup_sym.py CA_WAIT_FOREVER      # a define (value), a type (members), an enum value
tools/lookup_sym.py --list ca_uart       # every symbol with a prefix
tools/lookup_sym.py --find mutex lock    # by meaning: name or description has all the words
tools/lookup_qa.py ca_mutex_lock         # questions and answers: intent, common mistakes
tools/lookup_qa.py dma uart              # Q&A that mention all the words
tools/lookup_qa.py -n 30 dma uart        # more results (default 10)
tools/lookup_qa.py --type error ca_uart_put   # one kind: usage code parameters return error behavior hw_diff
```

**The data** (`tools/db/`, plain files, no network):

| File | Content | Trust |
|---|---|---|
| `reference.json` | the reference chapter of the manual: ~1300 functions, ~740 defines, ~220 types, ~40 enums — signature, header, parameters, return, notes, example | description written partly with an AI from the code; signatures and headers are extracted, not written |
| `caos_qa.jsonl` | ~5800 question/answer pairs generated by an AI from that reference: intent, typical use, common mistakes, differences between boards | good for the *why*, can be wrong in details |

**Order of use**: `lookup_sym.py` for the exact name and signature, `lookup_qa.py` for how
it is meant to be used, then an example that calls it (search `examples/` for the name),
and the declaration in `include/` when a detail matters: **the header is the authority**.
Both tools exit with status 0 when something is found and 1 when nothing is, so they can
be used in scripts. When a name is not found, `lookup_sym.py` prints the closest names and
suggests `--find`.

**Do not invent function names by convention** — the real names often differ from the
"obvious" one (`ca_os_sleep`, not `ca_task_delay`; `ca_memory_allocate`, not
`ca_memory_alloc`). If `lookup_sym.py` does not know a name, it does not exist: say so
instead of guessing. The reference also documents CAN, USB HS and MicroPython, which the fixed FREE
configuration leaves off: when `lookup_sym.py` says *not declared in include/*, this FREE edition does not
have it (see `LIMITS.md`).
The examples remain the best usage reference.

## Running without a board

When the user has no board, or to try something before flashing it:

- **Renode on the user's PC** (`simu/`, guide in `simu/QUICKSTART.md`, limits in
  `simu/LIMITS.md`). It runs the same `.elf` that `./do` builds, unmodified:

  ```bash
  simu/run.sh h753 elfs/H753/h753_example_2.elf 5000 "help;top"   # headless: N ms simulated, then the output
  simu/run.sh -i u575 elfs/U575/u575_app_1.elf     # interactive console on /tmp/caos_u575
  simu/run.sh -i -e f767 elfs/F767/f767_example_35.elf   # + Ethernet to a host TAP (F439 F767 H753)
  simu/run.sh -w f767 elfs/F767/f767_example_29.elf 3000 "wire"   # + the bench jumpers of the example
  simu/test.sh                                     # the automatic Renode suites (robot)
  ```

  Boards: `f439 f446 f767 h563 h753 h773 u575`. Output and Renode log stay in `simu/out/`.
  In interactive mode the Renode monitor is on `telnet localhost 1234` (pause, registers,
  memory, peripherals): a way to look inside without a debugger.

**What to trust from a simulated run.** Faithful: boot, scheduler, tasks, MPU (stack
guard, XN), faults, FP context, timers and IRQs, the console, Ethernet with `-e`. Not
faithful: **time** (the core runs at a fixed reduced speed, so cycle counts, CPU percentages
and timeouts that depend on real time differ from the board), BFAR, unaligned-access traps;
USB, the clock tree and most accelerators are not modelled. A failure on Renode in one of
those areas says nothing about the board: confirm on hardware before changing code.

## Test bench

The package ships the bench that validates caOS (`test/run_test.sh`, guide in
`QUICKSTART.md` section 7): it flashes an example, talks to its console and judges each
phase. Network classes reconfigure the PC Ethernet port (`tools/bench_net.sh`, root): run
them only on a dedicated point-to-point link, never on an office or home LAN, and only when
the user asks. `./eol.sh` runs the whole bench on every board; the reports of the run made
before each release are published in the repository (`end_of_line/`).

## Code conventions

- Every `.c` includes only `#include "caos.h"`.
- Types: `u8 u16 u32 i8 i16 i32`, `bool`; strings are `c_str` (a pointer to a caOS string).
- Bare metal on CMSIS, **no ST HAL**. caOS owns the clock and the SysTick: do not add
  `SystemClock_Config()` or `HAL_InitTick()`.
- Console output is in English and ASCII.

## Program structure

```c
#include "caos.h"

static u32 worker(void *arg)          /* every task: u32 f(void *arg) */
{
    (void)arg;
    for (;;) {
        /* ... */
        ca_os_sleep(100);             /* ms */
    }
    return 0;                          /* returning ends the task cleanly */
}

void ca_os_configure(void) { /* drivers and services, before the scheduler */ }

void ca_os_main(void)
{
    ca_os_job("worker", CA_TH_LEVEL3, worker, NULL,
              STACK_MEDIUM, CA_JOB_STD, CA_FAULT_RESTART_THREAD);
    ca_os_run(true);                   /* starts the scheduler, does not return */
}
```

- `ca_os_job()` makes the task runnable at once; `ca_os_job_suspend()` creates it suspended
  (release it with `ca_os_resume_handle()`).
- Keep the returned `ca_task_handle_t`. Never store the numeric `thid`: it is a position in
  the task list and changes when another task is removed. A stale handle fails safely.
- Tasks that use floating point must be created with an FPU job type, not `CA_JOB_STD`.

## Semantics that differ from other RTOSes

- **Priorities are CFS weights**, `CA_TH_LEVEL0..6` = 1, 2, 4 … 64. A higher level gets a
  larger CPU share; it does **not** starve the lower ones. Never use priority as mutual
  exclusion: use a mutex, or `ca_os_sched_lock()` / `ca_os_sched_unlock()` (never block
  while holding it).
- **Timeouts are in milliseconds**, on every blocking call: `CA_NO_WAIT_TIME` (0) = do not
  wait, `CA_WAIT_FOREVER` = wait forever.
- **Wake-up order on IPC is FIFO**, not by priority.
- **An ISR does not preempt into the woken task**: the switch happens at the next tick
  (100-250 µs), or at once if the ISR interrupted the idle task. Put deadline-critical work
  in the ISR itself.
- A blocked wait cannot be aborted from outside: use a timeout and recheck a condition.
- `ca_os_delay_ms()` is a busy wait for **before** the scheduler; from a task use
  `ca_os_sleep()` / `ca_os_sleep_until()`.

## Memory

- `STACK_SMALL/MEDIUM/LARGE/XLARGE/KERNEL` are **fixed sizes chosen per board** in
  `objmap.h` (multiples of `STACK_SLICE`, 2 KB):

  | board | SMALL | MEDIUM | LARGE | XLARGE | KERNEL |
  |---|---|---|---|---|---|
  | F439, F446 | 2 KB | 2 KB | 4 KB | 6 KB | 8 KB |
  | F767, H773 | 2 KB | 4 KB | 6 KB | 8 KB | 10 KB |
  | H563, H753, U575 | 4 KB | 6 KB | 8 KB | 10 KB | 12 KB |

  Every class is at least as large as on the F4 boards, so a task sized on an F439/F446
  fits everywhere. Stacks are always allocated by the kernel, with MPU guard and canary;
  there is no user-supplied stack. Check the real use with `stack` or `taskall`.
- `ca_memory_allocate()` blocks **belong to the calling task** and are freed when it ends.
  A block handed to another task (message, buffer, shared object) must come from
  `ca_memory_allocate_shared()` and be freed with `ca_memory_free()`.
- **A CLI command with a stack in its table entry runs in a temporary task** (named after
  the command) that ends when the command returns: anything it allocates with
  `ca_memory_allocate()` is freed right after. Keep long-lived resources in a permanent
  task, or allocate them shared. A command with stack `0` runs inside the `cli` task
  itself: it must not allocate, block or take long (see "Console and CLI").
- The FREE edition reserves half of the heap (`LIMITS.md`).

## Console and CLI

- `ca_stdout_put_n()` / `ca_stdout_printf_n()` work **only from a task**. Before
  `ca_os_run()` (in `ca_os_configure()`) print with `PUT_N()` on a `PRIVATE_STRING`.
- User CLI commands are a **table**: `{ word, help line, { handler, stack } }`, registered
  once with `ca_cli_register_table()`:

  ```c
  /* the line arrives WITHOUT the command word */
  static bool motor_cmd(c_str *args)
  {
      const char *p = (*args)->data;
      if (ca_strncmp(p, "start", 5) == 0) { CLI_PUT_N("started"); return true; }
      if (ca_strncmp(p, "stop", 4) == 0)  { CLI_PUT_N("stopped"); return true; }
      return false;                     /* bad arguments: cli prints the help line */
  }
  static const ca_cli_cmd_t s_motor_cmds[] = {
      { "motor", "motor     : start | stop", { motor_cmd, STACK_SMALL } },
  };
  static ca_cli_table_t s_motor_table = {
      "motor", s_motor_cmds, (u16)(sizeof(s_motor_cmds) / sizeof(s_motor_cmds[0])), NULL
  };
  /* in ca_os_configure(), after ca_cli_init(): ca_cli_register_table(&s_motor_table); */
  ```

  The word is matched **exactly**; `help` lists the help lines of every table. The handler
  returns `true` when done, `false` to have the help line printed. The table is `const`
  (flash), the `ca_cli_table_t` node lives in RAM and must be `static`.
- **Stack `0` or a real stack.** With `0` the handler runs inside the `cli` task: only for
  what ends in well under 50 ms and does not allocate, or the console stops answering.
  Anything slower declares a stack (`STACK_SMALL`...) and runs in its own task, one
  instance per command: typing it again while it runs prints `busy: ...`. The console
  stays free meanwhile.
- An `EN_CLI_x` flag only compiles a driver's commands; they appear when that driver's
  `_init()` runs (it registers the driver's table).

## Drivers: traps worth knowing

- **Pins are board facts.** The same signal sits on different pins/connectors on each
  Nucleo; the examples carry per-board `#if MCU_ID == ...` blocks. LEDs come from `objmap.h`
  through `ca_led_*()` — use those rather than hard-coded GPIOs.
- `ca_uart_*` numbers start at 1: `uart_num == 0` is rejected. LPUART has its own API
  (`lpuart.h`).
- PWM: the period is **ARR+1** timer ticks and duty is in permille; ARR is derived from the
  timer clock, which differs per MCU.
- Debugging the FREE firmware with a halting debugger is not supported (`LIMITS.md`): debug
  from inside, through the console. To read the user's variables, take the address from
  the `.elf` and ask the board: `./peek.py <elf> <name> -p <port>` (globals and statics;
  `--set HEX` writes a 32-bit word), or the CLI directly (`mem <addr> [value]`,
  `hexdump <addr> <lines>`, hex without `0x`). To follow a value over time, a low-level
  task that prints it when it changes. Also `top`, `taskall`, `free`, `canary`, `mpu`,
  `memmap` and the safeguard messages. Read the board before guessing from the code.

## Lessons from the bench

Each item below cost real debugging time on the boards. Symptom first, then the rule.
They describe how caOS and the Nucleo boards behave, so they stay true for user code.

**Tasks and memory**

- *A task index printed at launch names another task a moment later.* A `thid` is a
  position in the task list and moves when any task ends; every CLI command with a stack
  runs in a temporary task of its own. Keep the `ca_task_handle_t` from `ca_os_job()`; a stale handle fails
  cleanly instead of hitting another task.
- *`Invalid Free` or a fault in the allocator, one command after the real cause.* Heap
  allocated inside a CLI command handler (one with a stack) is freed when the command
  returns. Open, use and
  close in the same command, or let a permanent task own the resource (or allocate it
  with `ca_memory_allocate_shared()`).
- *A task prints `Invalid call without Context` at start-up.* A task runs as soon as it is
  created, and `ca_stdout_*` needs a running task. In `ca_os_configure()` print with
  `PUT_N()` on a `PRIVATE_STRING`.
- *A stack that was fine on one board overflows on another.* The `STACK_*` sizes are set
  per board (see "Memory"): the F4 boards have the smallest. Size on an F439/F446, then
  check `stack` / `taskall` on the board.
- *A wait meant as a poll never returns, or the reverse.* Timeouts are milliseconds on
  every blocking call: `CA_NO_WAIT_TIME` (0) does not wait, `CA_WAIT_FOREVER` waits forever.
  Never write a literal `0` meaning "forever".

**Console and timing**

- *Printing slows the task, or a line goes missing with `stdout: warning queue is full!`.*
  The console is a queue drained by its own task at the UART speed (115200 baud is about
  11 characters per ms). Near full, the printing task is slowed by 1-5 ms per line; after
  1 s with the queue full the line is dropped. Do not print inside loops whose timing
  matters. `ca_stdout_flush()` discards the queue, it does not wait for it.
- *A cycle count that changes between builds or between two runs.* A measurement taken
  right after a print also measures the console task. Time short sections between
  `ca_enter_critical()` and `ca_exit_critical()`, reading the cycle counter inside, or let
  the console drain first. If the same thing measured twice in one run differs, it is the
  environment, not the code.
- *A polled transfer on a short hardware FIFO (SAI, SPI) overruns, but only right after a
  command.* The console is still sending the echo and takes the CPU in chunks of hundreds
  of microseconds. Wait for it to finish, or use DMA, which is the right tool for streams.
- *Printing a `u32`.* Use `%u`, `%d`, `%X`: the caOS formatter ignores `l` and `h`, and every
  integer is 32 bits. Console text is English and plain ASCII.

**Boards and pins**

- *The driver configures the pins without error, and nothing comes out.* The reference
  manual says which pins *can* carry a peripheral; the board user manual says which ones
  reach a connector and are not already used (LED, ST-LINK VCP, solder bridges). Wire
  from the example's per-board pin table, and use its `wire` command where it has one:
  it checks the jumpers before the test.
- *NUCLEO-U575ZI-Q*: I2C1 on PB6/PB7 does not work (PB7 drives the blue LED through a
  transistor); PB10/PB11 are routed elsewhere by default solder bridges. Use I2C2 on
  PF1/PF0 (the Zio "I2C_B", CN9-19/21) or I2C4 on PF14/PF15, **with external 4.7 kΩ
  pull-ups**: the internal ones read 3.3 V on a meter but do not make I2C work. LPUART1 is
  driven on PA2/PA3 (CN9-3/CN9-1), not on the D0/D1 pins printed as USART_A.
- *`ca_uart_init(0, ...)` returns false.* UART numbers start at 1. LPUART has its own API
  (`ca_lpuart_init()`), and cannot be used through `ca_uart_*`.
- *PWM at 100% still drops for one tick, or a test says duty cannot reach the top.* The
  period is ARR+1 ticks and full duty is CCR = ARR+1. ARR comes from the timer clock of
  the board: read it, do not hard-code it.
- *DMA reports a complete transfer and the CPU reads old data* (only if the user turns
  the D-cache on, on F7/H7). caOS leaves the M7 D-cache **off** (I-cache on) so that DMA
  buffers need no cache maintenance; the CLI `mem`/`hexdump` also read through the cache.
  Turning it on is the user's choice and the user's cache maintenance.
- *An MPU region asked for in `ca_os_configure()` is gone after start-up.* Check the
  region with the `mpu` command **after** the scheduler runs; for a region that must
  last, prefer the last region index (`ca_mpu_get_total_regions() - 1`) with
  `ca_mpu_update_region()`: on overlap the highest index wins.

**Network**

- *Data missing in a TCP stream read in small pieces.* `ca_tcp_recv()` delivers one
  received segment per call and drops what does not fit in `buf_len`. Read into a buffer
  of at least one full segment (1460 bytes on Ethernet) and parse from there.
- *A second SSH or HTTP client is refused.* By design the SSH, HTTP (and, in the full
  edition, HTTPS) servers serve one session at a time.
- *VLAN-tagged traffic is ignored.* Only untagged frames and priority tags (VID 0) are
  accepted; frames with a VLAN id are dropped and counted (`ip stats`). Put the board on an
  access port of the switch.

**Tests**

- *"It compiles and the code looks right."* The verdict comes from the board: run the
  example, read the console, and compare with what the example prints as its result.
  Comments and documentation can be older than the code; the board is not.
- *A test passes on Renode and fails on the board, or the reverse, on timing.* Renode time
  is not real (fixed reduced speed): cycle counts, CPU percentages and real-time timeouts
  only mean something on hardware.

## Faults

Each task has its own fault policy (the last argument of `ca_os_job()`):
`CA_FAULT_RESTART_THREAD` restarts it, `CA_FAULT_ASSERT` removes it, the emergency variants
call a handler first. A fault in one task does not stop the others. `CA_SAFEGUARD(cond, msg)`
is the assert; it uses the same mechanism.
